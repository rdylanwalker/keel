# Known Limitations

Keel is alpha software. This page collects the limitations and open bugs a user is likely to hit, with workarounds where one exists.

## Releases and Scope

- **No upgrade path.** A release marked breaking in the changelog (a `!` or `BREAKING CHANGE` entry) does not migrate clusters, GitOps repositories or tenant repositories. Start over with a fresh `keel bootstrap init` on a new cluster and a new repository.
- **Local Docker socket flag is unsafe for tenants.** `--local-dev-docker-socket-exception`, used in the Quick Start for nested `kind` clusters, exposes the host Docker socket without authentication to PKO workspace pods and to any tenant pod that sets the workspace label. That is root on the host, so tenant isolation does not hold with this flag. Use it on throwaway machines only.
- **Single-node management cluster.** The management cluster is a single node with no high availability.
- **Tested path.** The live E2E suite covers only local `kind` with the in-cluster Forgejo and Rauthy. Everything else is experimental; see the maturity table in the [README](https://github.com/rdylanwalker/keel#maturity-what-is-tested).
- **Platforms.** Only Linux x86_64 (including WSL2) is tested. Release binaries for Linux arm64, macOS arm64 and Windows x86_64 are built but not tested. There is no macOS Intel build.

## Bootstrap Targets

- **Cloud bootstrap is untested.** `--target aws|gcp|azure` installs single-node k3s on a 4 GB VM (`t3.medium`, `e2-medium`, `Standard_B2s`). These are not free-tier sizes. No automated test runs them, and the local management node alone peaks at about 7 GiB of memory, so 4 GB is probably too small.
- **Proxmox VE and Hetzner bootstrap are untested.** `--target proxmox` and `--target hetzner` install single-node k3s on an 8 GB VM and continue with the seed install, like the cloud targets, but no automated test runs them. Proxmox needs a cloud-init template (default VM `9000`) with `qemu-guest-agent` and its boot disk on `scsi0`, and an API token that can read guest-agent data. The workstation must reach the VM on ports 22 and 6443 (see [Stage 0 Bootstrap](../getting-started/bootstrap.md#proxmox-ve-and-hetzner)). `--distro talos` is refused for both; install Talos yourself and use `--target kubeconfig`. The Proxmox program creates no host firewall, so 22 and 6443 are open to everything on the VM's bridge network; isolate it with a VLAN or a PVE firewall.
- **The `proxmox-k3s-cluster` blueprint is untested.** It installs single-node `k3s` over SSH from the tenant's PKO workspace pod and writes the admin kubeconfig to the tenant's `<instance>-kubeconfig` Secret, but no automated test runs it. The workspace pod must reach the Proxmox VE API and the VM on TCP `22` and `6443` (private addresses are allowed only on 22, 443, 6443 and 8006), and Flux on the management cluster must reach the VM on `6443`. Like the Stage 0 program, it creates no host firewall, so 22 and 6443 are open to everything on the VM's bridge network, which is wider than the cloud security groups. Changing `kubernetesVersion` after creation does not upgrade k3s (see [Proxmox VE workload clusters](../catalog/provider-examples.md#proxmox-ve-k3s-cluster-proxmox)).
- **Local Git only.** With `--repo-dir` and no `--with-forge` or network `--git-url`, Flux cannot read the repository: merged changes are never deployed, `keel infra provision` fails with `409 ... is not a network Git URL`, and there is no tenant isolation. Use `--with-forge` or `--git-url`. The `409` says to re-run `keel bootstrap init` with `--with-forge` or a network `--git-url`, and the bootstrap summary prints `Flux Polling: inactive (...)` in this mode.

## Storage and Recovery

- **The in-cluster Forgejo is ephemeral.** `--with-forge` installs Forgejo with persistence disabled. Replacing the Forgejo pod deletes every repository, tenant repositories included. Mirror anything you want to keep.
- **The state escrow lives in the same cluster.** Stage 0 copies its Pulumi state to the in-cluster SeaweedFS. `keel bootstrap recover` repairs a damaged control plane while the cluster is reachable; it is not a backup against losing the cluster. Copy `~/.config/keel/stage0/<cluster>/` and the passphrase somewhere else.
- **Teardown leftovers.** `kind delete cluster` leaves `./keel-gitops`, `./keel-gitops.git`, `./keel-gitops-tenant-repos/` and `~/.config/keel/stage0/<cluster>/`. A later bootstrap with the same names silently reuses the old bare repository and its history. Delete them when you delete the cluster.

## Git and Forges

- **Gitea cannot host tenant repositories.** Gitea has no repository-scoped tokens. Use Forgejo 15 or later, GitHub or GitLab.
- **External forges are untested against real services.** GitHub, GitLab and external Forgejo are only tested against a mock forge.
- **The local clone pulls only while `keel serve` runs.** With `--with-forge`, the remote of `./keel-gitops` is the Forgejo port-forward that `keel serve` opens (`http://127.0.0.1:3000/...`), so nothing answers there once the server stops. `keel serve` stores the Forgejo token in a repository-local Git credential file (`.git/keel-credentials`, mode `0600`, used only for that remote's origin; the remote URL never contains the token), so `git pull` works while it runs, and removes the file and the helper again when it stops. That file holds the platform's Forgejo admin token while the server runs: treat the working copy like the kubeconfig, and delete `.git/keel-credentials` by hand if `keel serve` was killed (`kill -9`) instead of stopped.
- **Two proposals that change the same app conflict.** Keel rebuilds a proposal that fell behind `main` when it only conflicts in the generated `kustomization.yaml` index (see [Merging a proposal that is behind `main`](cli.md#merging-a-proposal-that-is-behind-main)). If two open proposals change the same app or Stack, the second one's merge is refused with the conflicting files. Close it and propose the change again.
- **GitHub tenant repositories pin GitHub's SSH host keys.** Keel writes `known_hosts` from GitHub's published host keys when it issues a tenant's deploy key, and copies the same keys into `keel-system/keel-pko-ssh-known-hosts`, which the PKO operator uses to follow each tenant Stack's `main` branch. If GitHub rotates its host keys, tenant clones and Stack branch tracking fail until you run `keel tenant repair-credentials <id>`, which issues a new key with fresh host keys and rewrites that ConfigMap. Tenant repositories on GitHub are always cloned over `ssh://git@github.com:22`, so the cluster needs port 22 egress. GitHub-hosted tenant Stacks are tested against a mock forge only, not against GitHub itself.
- **GitHub Free cannot protect private tenant repositories.** Branch protection on private repositories needs a paid GitHub plan, so the forge does not block direct pushes there.
- **Forgejo repository names are visible to other tenants.** A tenant's repository-scoped Forgejo token can read the name and description of other tenant repositories, but not their content.
- **Tenants created through the API on the Local Git provider.** They have no tenant Git source: Pulumi Stacks and previews return `409`, and Flux manifest apps never reconcile. Helm apps work.
- **Route hosts, instance names and once-per-cluster add-ons are first come, first served.** Keel refuses a proposal whose route or canary host another committed app already routes, whose derived Flux `Kustomization` names (`<name>-config`, `<name>-canary`) overlap another instance's, or that adds a second copy of a once-per-cluster add-on (for example `kyverno` or `keel-server`) to the same workload cluster. These checks read only what is merged on `main`, so two open proposals are not checked against each other: when both merge, the second one's routes lose to the first, its duplicate `Kustomization` can stop tenant reconciliation, or its operator fights the first. Review open proposals before merging. Kyverno does not enforce host uniqueness either. A tenant that writes routes directly (for example by merging its own PR outside Keel) can claim a host first. On an exact-hostname tie, Gateway API keeps the older route, so that tenant then serves another tenant's host.
- More tenancy gaps, such as the operator token on external forges and the platform `age` key, are listed in [Security & Tenancy: Residual exposure](../operations/security-and-tenancy.md#residual-exposure).

## Apps and Canaries

- **Editing an infrastructure stack does not keep its secrets.** Apps (Helm and manifest) and bundle items keep a secret field left blank on Edit, but a stack re-encrypts only the secrets you submit. The web UI's Edit form keeps stack secret fields required, so re-enter every one.
- **The web UI cannot clear a stored secret.** A secret field left blank on Edit keeps its stored value. To unset an optional secret, submit `""` for it through the API or a CLI values file.
- **Canary analysis is not tested.** E2E checks that a canary deploys and initializes, but not traffic shifting, promotion or rollback.
- **Apps are served over HTTPS only.** Canary apps are reachable through `keel-ingress` at `https://<host>:8888` on local `kind`. Plain HTTP on port 8888 does not respond.

## Operations

- **Slow, silent first preview.** The first PKO preview pulls the 3.5 GB PKO workspace image. `keel preview status --watch` prints nothing for a few minutes while this happens. `kind` nodes pull images in parallel, so other pods keep starting meanwhile, but k3s nodes on the VM targets still pull one at a time and the other pods on the node wait behind it. Keel pins the image to an exact tag (`keel_pko::PKO_WORKSPACE_IMAGE`, currently `pulumi/pulumi:3.277.0-nonroot`), so you can pull it once and load it into the node: `docker pull <image> && kind load docker-image <image> --name keel-mgmt`.
- **A Stack stalled on a deleted Git credential Secret recovers only through keel-server.** If the Secret a tenant Stack's `gitAuth` reads (`tenant-<id>/keel-gitops-credentials`) is deleted, PKO marks the Stack `Stalled` (`SpecInvalid`) and never retries it on its own. Once the Secret exists again, keel-server requests a reconcile of the Stack: right away after `keel tenant repair-credentials` or `POST /api/v1/tenants`, otherwise within about a minute (and up to two more times if PKO still saw the old state). If keel-server is running but you do not want to wait, click **Reconcile Now** on the Stack. Without a running keel-server (for example after a `keel bootstrap init` re-run before the server starts), run `kubectl annotate stack <name> -n tenant-<id> pulumi.com/reconciliation-request="$(date +%s)" --overwrite`.
- **`keel serve` needs the hosts entries too.** If `idp.keel.local` does not resolve on the machine running `keel serve`, OIDC discovery fails and nobody can log in. Add the `/etc/hosts` entries before starting the server. `keel serve` logs a warning with the cause and the hosts-file fix at startup, and the login endpoint answers `503` (an error page in the browser) pointing at that log.
- **`kill -9` orphans `keel serve`'s port-forwards.** `keel serve` stops its `kubectl port-forward` children on Ctrl+C, `SIGTERM` and `SIGHUP`, but not on `kill -9`. If port `8888` (or `3000`) is still taken at the next start, it logs which port is busy and how to find and stop the leftover process.
- **Credentials in the bootstrap output.** The bootstrap summary prints the generated admin password in plain text. Keep that terminal output private, or pass `--admin-password` / `KEEL_ADMIN_PASSWORD`.
